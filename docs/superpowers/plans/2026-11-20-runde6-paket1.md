# Runde 6 · Paket 1 (Eventtypen + „ab“-Datum) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Es gibt zwei neue Eventtypen, und Event-Aufgaben bekommen ein optionales „ab“-Datum.

**Architecture:** Die Eventtypen sind eine rein additive Erweiterung der Konstante `EVENT_TYPES` (Domain und Web) plus i18n und Report-Maps.
`startDate` ist ein optionales Feld an `EventTask` (JSON-Store `event-tasks`). Bestandsaufgaben haben das Feld nicht, `withTaskDefaults` ergänzt beim Lesen `null`.

**Tech Stack:** Hono + zod (API), React + TanStack Query (Web), Vitest, Biome.

**Spec:** `docs/superpowers/specs/2026-11-20-runde6-feedback-design.md` (Abschnitte 11, 14)

## Global Constraints

- Bestehende Events und Aufgaben werden nie umgeschrieben (kein Backfill). Neue Felder sind optional und bekommen beim Lesen einen Default.
- Die Oberfläche ist zweisprachig, `de.json` und `en.json` werden immer gemeinsam gepflegt.
- Die Typ-Keys sind `top_management_circle` und `management_circle`, die Labels DE „Top-Management-Zirkel“ und „Management-Zirkel“, EN „Top Management Circle“ und „Management Circle“.
- Die Überfällig-Logik hängt weiterhin nur an `dueDate`.
- Vor dem Push gelten Biome-Format und der LF-Check (siehe Memory mexp-lint-crlf).

## Review Focus

- PATCH mit `startDate: null` löscht das Datum, PATCH ohne `startDate` lässt es unverändert. Test in Task 2.
- Liegt `startDate` nach `dueDate`, antwortet die API mit 400 `INVALID_DATE_RANGE`. Test in Task 2.
- Eine Bestandsaufgabe ohne Feld liefert `startDate: null` in der API-Antwort. Test in Task 2.
- Aus Blueprints übernommene Aufgaben haben `startDate: null`. Abgedeckt durch `withTaskDefaults`, der bestehende blueprint-apply-Test läuft weiter.
- Die neuen Typen erscheinen im Event-Filter, im Anlegen-/Bearbeiten-Dialog und bei den Blueprints automatisch über `EVENT_TYPES.map`, eine manuelle Prüfung im Dev reicht.
